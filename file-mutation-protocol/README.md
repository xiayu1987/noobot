# File mutation contract

Patch updates use ordered, non-overlapping hunks against the original snapshot. In `apply_patch`, `@@ L<line>` identifies the exact original start line; bare `@@` requires a unique continuous match at or after the previous hunk's end. Every hunk must contain an addition or removal. Context-only hunks never establish scope for later hunks. `read_file_numbered` derives the same exact anchor from consecutive old-line numbers; it does not change matching semantics.

`baseVersions` is optional. When omitted, the runtime captures successful `read_file` results visible in the generating model request and binds their versions to its returned tool calls. File identity uses canonical locators, not resource IDs. Later reads cannot change that request snapshot. Ordered read batches replace earlier observations; different hashes in the same batch remain ambiguous and require rereading. Missing or unavailable read history also requires rereading. Added destinations must be absent; unread move destinations must be absent. A read version is required to overwrite an existing move destination. The runtime never substitutes a write-time hash for a read baseline. Explicit `baseVersions` must cover every source and destination without duplicates, including absent destinations with `sha256: null`; invalid explicit versions are never replaced by captured reads. All versions pass the same lock-protected validation before any mutation is committed.

Read observations apply only to mutable file locators (`workspace`, `host`, `mount`). Attachment identities address immutable snapshots and never supply patch baselines, even when a read reports their content hash. Unknown or malformed file locators remain errors.

`normalizePatchInput` is the single input-normalization contract. It identifies the format and checks an explicit format against the content. For `apply_patch`, missing outer markers may be inserted. Headerless update hunks require an explicit `filePath` or a unique explicit `baseVersions.filePath`; the most recent read never selects the target. Mixed headerless hunks and file sections are rejected. `filePath` is accepted only for headerless updates. Normalization returns `adaptations`; it never removes context-only hunks, rewrites diff counts or selects an ambiguous source location.

`baseVersions.filePath` identifies the file in the same path view as the `read_file` result locator: use `path.path` for workspace-relative or host-absolute locators, and `${path.mount}/${path.path}` for mount locators. The mount prefix is part of the file identity; identical relative paths in different mounts are distinct targets. It is not a patch-header path and is never transformed by `strip` or `root`. These options apply only to patch headers. Callers supply the complete path for absent destinations. Implementations project resolved patch targets through the shared tool-path contract before indexing versions; root-relative version aliases are not accepted.

Hunk location failures retain the target `path` and report `details.hunkIndex` (1-based within that file) and `details.patchLine` (1-based header line in the submitted patch). Ambiguity reports `candidateLines` and nearby candidate text in the original source without selecting a candidate or inventing a failure `line`. A concrete source mismatch may include `line` and numbered `nearbyContent`. Syntax errors report `patchLine`; unchanged-hunk errors include the block text and explain how to rebuild the edit. Diff count errors report declared and actual counts. A failed plan writes no files. Recovery requires rereading the intended source, rebuilding the identified hunk and resubmitting it.

`applyFileMutation` accepts `stageBytes(stagedPath, bytes)`. The callback writes only the supplied sibling staging path and must not change the destination. The callback may fail before or after writing staging bytes. No destination commit has occurred at that point.

The transaction owns destination changes: validate staged SHA-256, recheck the original destination version, rename the staged file (or unlink for deletion), validate the committed version, then publish the mutation record. Only a successful destination syscall establishes committed state. A record failure restores the original byte snapshot after checking that the destination still matches this transaction's committed version. An external version conflict is reported without overwriting external content. Failure details distinguish `not_committed`, `restored`, `conflict` and `restore_failed`; cleanup failures retain their paths and errors alongside the primary failure. Rollback record cleanup failure reports `file_mutation_cleanup_failed` with `targetState: restored`. The old destination-writing callback is not accepted.

The package root exports browser-safe contracts and text validation. Node byte conversion is exported only from `@noobot/file-mutation-protocol/text-codec-node`; browser consumers must not import this entry.

Text encoding is owned by `decodeFileDocument`, `encodeFileText` and `resolveFileWriteEncoding`: supported encodings are UTF-8, UTF-16LE, UTF-16BE and GB18030. `auto` recognizes UTF BOMs and otherwise requires UTF-8; unmarked UTF-16 and GB18030 must be explicit. BOM conflicts, malformed Unicode and non-reversible byte conversions are rejected. Updates and moves preserve source encoding, BOM, unchanged line terminators and EOF state. Auto writes preserve a decoded source encoding; new files use UTF-8. No encoding is inferred from a file extension or MIME type. Read/preview metadata and mutation downloads use the same resolved encoding; hashes and rollback always operate on original bytes.

Existing destinations must decode losslessly with the requested encoding before any write, including whole-file replacement. Decoding errors and BOM conflicts propagate; they never mean that the file is absent. Only an absent destination permits the new-file UTF-8 default. The encoding parameter describes both source decoding and output encoding, not a transcoding request.

`assertFileText` accepts well-formed Unicode, including NUL and other control characters. Successfully decoded content remains text in reads, previews, mutations, snapshots and downloads; content characters do not clear its resolved encoding or format metadata. Document-specific validation, such as JSON syntax, remains the caller's responsibility.

Search strictly validates each returned file once and checks returned match/context lines against that read. A mismatch fails explicitly rather than mixing snapshots. Only encoding metadata is retained between files. This check does not provide a filesystem-wide snapshot.

Locks serialize cooperating mutations. Version checks detect external changes at validation points; this is not a filesystem compare-and-swap or a crash-recovery journal.

`createFileDiff` returns a deterministic longest-common-subsequence edit script with unchanged `git-lines-v1` fields. Ambiguous equal-cost alignments have no prescribed placement. Common prefix/suffix and disjoint ranges are resolved directly; remaining ranges use divide-and-conquer LCS with row scores instead of a full matrix. Worst-case comparison time remains quadratic for interleaved inputs.
